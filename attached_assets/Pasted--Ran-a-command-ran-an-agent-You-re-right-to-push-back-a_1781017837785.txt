How it actually works
One LinkedIn app per tenant, many accounts under it. There are two separate tables:

tenant_platform_credentials (shared/schema.ts:2183) — one row per tenant holding the LinkedIn app's client_id / client_secret. Unique constraint on (tenant_domain, platform) enforces "one app per tenant."
social_accounts (shared/schema.ts:2120) — one row per connected identity (company page, you, Michelle), each storing its own OAuth access token plus an availableAuthors JSON listing every persona that login can publish as.
Your Synozur scenario, concretely
Register one LinkedIn Developer App, save its client_id/secret once at Tenant → Platform Credentials → LinkedIn (client/src/pages/app/marketing/platform-credentials.tsx:40).
Create three social_accounts rows: "Synozur Company Page", "Chris", "Michelle".
Click "Connect" on each — each click hits the same OAuth flow (server/routes/marketing-delivery.ts:401) using the same tenant app, but LinkedIn prompts whoever is at the keyboard to log in as themselves. Their token gets stored on that specific row.
Because the default scope includes rw_organization_admin (server/services/social-publishers/linkedin.ts:26), the callback also calls /v2/organizationAcls and pulls in any company pages that login admins. So when you connect and you're a Synozur page admin, the company page shows up under your availableAuthors and you can publish as the page from your row — you don't strictly need a separate "company" row unless you want isolated tracking.

LinkedIn gates the scopes you need (w_member_social, w_organization_social, rw_organization_admin) behind their Community Management API / Marketing Developer Platform programs. As a multi-tenant SaaS publishing on customers' behalf, Synozur needs to apply for that access on the one shared app. Self-serve dev apps only get basic OIDC scopes. If you haven't applied yet, that's the gating step — code changes are easy, the LinkedIn approval is the long pole.

Short answer: you can't avoid it. LinkedIn has no API path to post content without an OAuth app. The only choice is who owns it.

Why an app is mandatory
LinkedIn's posting APIs (/v2/ugcPosts, /rest/posts) require an OAuth 2.0 access token, and tokens can only be minted against a registered Developer App. There is no:

Username/password API (unlike Bluesky's app passwords)
Personal access token (unlike GitHub)
Service account / API key (unlike most B2B SaaS)
RSS-to-LinkedIn or email-to-LinkedIn ingest
The only things that don't need an app are read-only public profile scrapes (against TOS, gets you banned) or paid Sales Navigator/Recruiter APIs (different product, also app-gated).

What "Synozur owns one app" actually means for customers
The app is a registration record — Synozur clicks once at linkedin.com/developers, fills in a form ("App name: Synozur Orbit", "Logo: …", "Privacy URL: …"), and gets a client_id / client_secret. After that:

Customers never see the app, never create one, never paste credentials.
They click "Connect LinkedIn" → land on linkedin.com's "Synozur Orbit wants to access your account" consent screen → click Allow → done.
That's the same UX as connecting a Google account to any third-party tool. Identical pattern.
The "app" exists at LinkedIn for trust/branding/abuse-control reasons (so LinkedIn knows which third-party service is making API calls and can revoke it if it misbehaves). It is not a per-customer thing — it's a per-product thing.

The real cost
The only friction you can't engineer away is LinkedIn's approval process for the w_member_social / rw_organization_admin scopes. Synozur applies once (Community Management API + Marketing Developer Platform), waits a few weeks, gets approved, and from then on all customers onboard frictionlessly. Without that approval, the app exists but can only do OIDC login — no posting.

Because LinkedIn's API will not issue an access token without one. That's it — it's a LinkedIn rule, not our code.

Every LinkedIn API call requires an access_token in the Authorization header. The only way to mint one is the OAuth 2.0 token endpoint, which requires client_id + client_secret as request parameters. Those two values are the app — registering the app is just LinkedIn handing you that pair.

There is no alternative mechanism. LinkedIn has no:

Username/password auth
Personal access tokens (GitHub-style)
API keys (Stripe-style)
App passwords (Bluesky/Apple-style)
Service accounts (Google Cloud-style)
So "no app" = "no posting to LinkedIn, ever." The only legal way around it is browser automation against linkedin.com, which violates their TOS and gets accounts banned within days.
